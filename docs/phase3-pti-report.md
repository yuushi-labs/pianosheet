# Phase 3（`0.4.0-phase2`）PTI-ONNX 組み込みレポート

ピアノ専用モデル PTI（ByteDance「High-resolution Piano Transcription with Pedals by
Regressing Onset and Offset Times」の音符枝を ONNX 化したもの、`piano-notes-v1.onnx`、
98,689,388 B、CC BY 4.0）を最終解析エンジンとしてアプリに組み込み、後処理・ノイズ前処理・
端末コストを実測で調整した記録。比較実験（どのモデルを積むか）は
[phase2-4-pianovam-report.md](phase2-4-pianovam-report.md) と
`work/pianovam_models/REPORT_スマホ内モデル比較.md` を参照。

測定条件は前回と同じ PianoVAM v1.2 の6曲×40秒（計2,220正解音符）、採点も同じ
（onset ±50 ms の1対1マッチ、micro F1、和音一致、同音重複）。測定コードは
`work/pianovam_models/tune_pti.py`。

---

## 0. 結論

1. **後処理パラメータを動かしても Offset 誤差は改善しない。** 閾値4種×近傍4種の
   69通りを総当たりし、F1 が最も上がるのは `onset_threshold=0.5`（0.9571→0.9603）だが
   和音一致が 0.9113→0.885 に落ちる。**公式値（0.3 / 0.3 / 0.1、近傍2 / 4）を既定のまま**採用。
2. **一様な Offset バイアス補正は効かない。** 曲ごとに誤差の向きが違い（pv60 +286 ms、
   pv70 +139 ms、pv74 −10 ms、pv9 −7 ms）、3曲で当てた補正を残り3曲に当てても
   中央値が平行移動するだけで p95 は悪化する。**不採用**。
3. **代わりに「減衰トリム」を採った。** 音符の終端を、その鍵のキー活動（frame output）が
   ピークの40%未満に5フレーム（50 ms）連続で落ちた位置まで詰める。
   **Offset中央値 +102 → +58 ms、p95 607 → 508 ms、長さ誤差中央値 +110 → +69 ms、
   F1・和音一致は不変**（改善32音 / 悪化4音）。Kotlin の既定として実装し、単体テストで固定。
4. **電話マイクのノイズ下では Denoiser「弱」が最も効く**（F1 白12dB 0.9208→0.9417、
   ピンク12dB 0.9054→0.9341、高域傾斜 0.9434→0.9491）。ただしクリーン音源では
   和音一致を落とすので、**最終解析の既定は現行どおり「標準」**（PTI の前段は今のパイプラインのまま）。
5. **端末コストは 40秒で7.7秒（2コア、実時間の5.2倍速）**、10秒区間あたり1.09秒、
   セッション生成0.17秒、ピークRSS 1.2 GB。**10秒区間ごとに進捗を出せる**ので、
   解析中画面は「区間推論 n/N」を実測どおりに出せる。1スレッドなら 896 MB / 13.5秒。
6. **APK は 192 MB**（183 MiB）。500 MB 予算内。`assets/models/piano-notes-v1.onnx` は
   `noCompress += "onnx"` により STORED で格納され、インストール時の展開を待たずに
   ONNX Runtime が読める。

## 1. 後処理パラメータの掃引（Offset 誤差）

`RegressionPostProcessor` の `onset_threshold` / `offset_threshold` / `frame_threshold`
と、ピーク判定の近傍（onset 側 2 / offset 側 4 が公式値）を振った。推論は1回だけ行い、
その生出力に対して後処理だけを差し替えている（`tune_pti.py sweep`）。

| 設定 | micro F1 | 和音一致 | 検出音符 | Offset中央値 | Offset p95 |
|---|---|---|---|---|---|
| **公式 0.3 / 0.3 / 0.1** | 0.9571 | **0.9113** | 2,206 | +102 ms | 607 ms |
| onset 0.2 | 0.9500 | 0.920 | 2,256 | +102 ms | 607 ms |
| onset 0.4 | 0.9587 | 0.894 | 2,165 | +102 ms | 607 ms |
| onset 0.5 | **0.9603** | 0.885 | 2,133 | +102 ms | 607 ms |
| offset 0.2 / 0.4 / 0.5（onset 0.3 のまま） | 0.9571 | 0.911 | 2,206 | +102 ms | 607 ms |
| frame 0.05 / 0.15 / 0.2（onset 0.3 のまま） | 0.9571 | 0.911 | 2,206 | +102 ms | 607 ms |
| 近傍 onset2/offset2・2/6・3/4・4/4 | 0.9566–0.9571 | 0.910–0.911 | 2,203–2,206 | +102 ms | 607 ms |

- Offset 側の閾値と近傍は**まったく誤差を動かさない**。理由は後処理の構造で、
  終端は「offset の回帰ピーク」と「frame output の消失」の近いほうが採られるため、
  閾値を上下しても両者が同じフレームを指すかぎり結果が変わらない。
- F1 を上げる方向（onset を上げる）は「曖昧な打鍵を捨てる」方向なので、和音の
  取りこぼしが増える。**和音一致 0.911 を守る公式値が最良**と判断した。
- `frame_threshold` は 0.05–0.2 の範囲で無影響（終端が offset 側で決まるため）。

**Offset 誤差の中身**（公式値、ペダル無し音符）: 曲ごとの中央値は
pv60 +286 ms / pv70 +139 ms / pv74 −10 ms / pv9 −7 ms、pv29 と pv12 は
ペダル無し音符がほぼ無いため対象外。外れ値は「短い音符をモデルが響きの長さぶん
伸ばす」ケースで、pv70 の 0.11 秒の打鍵が 1.29 秒になっていた。
つまり誤差は**モデルの note-off が減衰を拾いすぎる**ことが原因で、閾値では動かない。

### 1.1 一様バイアス（不採用）

学習側3曲（29/60/74）で最適な −0〜−120 ms を探し、検証側3曲（12/9/70）に当てた。

| バイアス | 学習側 中央値 / p95 | 検証側 中央値 / p95 |
|---|---|---|
| ±0 ms | +102 / 1,895 | +102 / 3,708 |
| −40 ms | +62 / 1,919 | +62 / 3,755 |
| −100 ms | +2 / 2,086 | +2 / 4,220 |

中央値は狙いどおり 0 に寄るが、p95 は単調に悪化する。曲ごとに誤差の向きが違うので
一様補正は「当たっている曲を壊す」だけだった。**採用しない。**

### 1.2 減衰トリム（採用）

`frame_output`（その鍵が押されている確率）は、回帰された note-off より先に落ちる。
そこで「音符の始点〜終端の区間で、frame output がピークの X% 未満に N フレーム
連続で落ちた最初の位置」まで終端を詰める（ただし音長 60 ms は下回らない）。
X と N を振った結果:

| 設定 | Offset中央値 | Offset p95 | 長さ誤差中央値 | 改善/悪化（音符数） |
|---|---|---|---|---|
| トリムなし | +102 ms | 607 ms | +110 ms | — |
| X=0.2 | +73 ms | 539 ms | +83 ms | 27 / 14 |
| X=0.3 | +61 ms | 537 ms | +71 ms | 38 / 38 |
| X=0.4 | +54 ms | 487 ms | +64 ms | 45 / 63 |
| X=0.5 | +46 ms | 412 ms | +56 ms | 44 / 94 |
| X=0.7 | +14 ms | 406 ms | +24 ms | 56 / 177 |
| **X=0.4 + 5フレーム連続** | **+58 ms** | **508 ms** | **+69 ms** | **32 / 4** |
| X=0.3 + 5フレーム連続 | +71 ms | 521 ms | +81 ms | 26 / 3 |
| X=0.4 + 15フレーム連続 | +64 ms | 510 ms | +74 ms | 22 / 1 |

- **「連続して落ちていること」を条件にすると悪化がほぼ消える**。単発の落ち込みで
  保持音を切ってしまう事故（X=0.4 の 63 音）が、5フレーム（50 ms）の持続条件で 4 音まで減る。
- X=0.4 / 5フレームを採用。**F1 0.9571・和音 0.9113 はそのまま**（トリムは終端だけを
  動かすので onset マッチに影響しない）。曲別では pv70 が +139 → +8 ms と改善し、
  pv74 / pv9 は −10 → −11 / −7 → −9 ms とほぼ不変。
- pv60 の +286 → +243 ms は残る（速い減衰の和音で、frame output 自体が高いまま）。
  これは後処理では解けない領域で、ペダル枝を持つ完全版モデルか、減衰の物理モデルが要る。

## 2. ノイズと Denoiser

PianoVAM の excerpt（44.1 kHz）に人工ノイズを混ぜ、アプリの `Denoiser`
（`pianosheet_poc/denoise.py` = Kotlin 実装の Python 双子）を前段に通してから
16 kHz に落として PTI に渡した。ノイズは信号電力比で SNR を定義。

| 入力 | Denoiser off | weak | standard |
|---|---|---|---|
| クリーン | **0.9571** / 和音 0.911 | 0.9597 / 0.894 | 0.9464 / 0.861 |
| 白色 SNR 20 dB | 0.9448 / 0.904 | **0.9496** / 0.872 | 0.9431 / 0.850 |
| 白色 SNR 12 dB | 0.9208 / 0.898 | **0.9417** / 0.873 | 0.9356 / 0.843 |
| ピンク SNR 12 dB | 0.9054 / 0.870 | 0.9341 / 0.861 | **0.9343** / 0.835 |
| 高域傾斜 SNR 12 dB | 0.9434 / 0.899 | **0.9491** / 0.867 | 0.9419 / 0.836 |

（数値は micro F1 / 和音一致。Offset 中央値は off より weak のほうが小さく、standard が最小。
例えばピンク12dB: 101 → 78 → 55 ms。）

- **ノイズ下では weak が最も F1 を守る**。PTI は入力の対数メルをモデル内で作るので、
  スペクトル減算の「弱い」設定くらいがちょうどよい。standard は F1 を少し落として
  和音一致をさらに削る（引きすぎ）。
- **クリーン音源では weak が和音一致を削る**（0.911 → 0.894）。PianoVAM は
  Disklavier のクリーン録音で、減算が倍音の裾を削るため。
- したがって「端末の設定（標準／弱）」をそのまま PTI の前段に使う現行構成を維持する。
  設定画面の「ノイズ除去」はユーザーが選ぶもので、PTI 固有の前処理を勝手に
  上書きしない。**スマホの実マイクで一度録って、標準と弱を見比べるのが次の確認点。**

## 3. 速度・メモリ

検証機（x86_64 2 vCPU / 3.5 GB、ONNX Runtime の CPU 実行プロバイダ）。Android の
ARM 実機では絶対値が変わるため、APK の実機計測が最終確認になる。

| | 1 スレッド | 2 スレッド |
|---|---|---|
| セッション生成 | 0.20 s | 0.17 s |
| 読み込み直後 RSS | 274 MB | 901 MB |
| 10秒セグメント（2回目以降） | 3.31 s（初回 2.70 s） | **1.09 s**（初回 1.84 s） |
| 40秒（7セグメント） | 13.55 s | **7.68 s** |
| 実時間比 | 2.9 倍速 | **5.2 倍速** |
| ピーク RSS | 896 MB | 1.20 GB |

- **1セグメント 1.09 秒**なので、解析中画面の「区間推論 n/N」は 1 秒ごとに進む。
  40秒の演奏で 7 区間＝約8秒、3分で 35 区間＝約40秒。
- メモリは「区間ごとに推論 → 中央50%だけを蓄積 → セグメント配列は即解放」で
  測っている（アプリの実装と同じ）。全セグメントを保持する方式だと 3 分区間で
  1 GB を超えるので、実装は必ずこの逐次方式にしている。
- **空き RAM が 1.4 GB 未満の端末では PTI を諦めて Basic Pitch で解析する**
  （`AppContainer.MIN_PTI_FREE_MB`）。`OutOfMemoryError` も捕捉して同じ経路に落ちる。
  解析ログ（`FinalTranscription.engineFallback`）と解析中画面に理由を出す。
- 94 MB のモデルは assets から `filesDir/models/` へ初回だけコピーする
  （ONNX Runtime はパスでセッションを作るため）。コピーは一時ファイル経由で、
  途中で落ちても壊れたファイルを掴まない。
- **セッションは解析中だけ持つ**: 解析開始時に生成し（0.2 秒）、音符が出たら即座に
  `close()` する。次回また作る。約1GBの常駐を避けるための措置で、例外・OOM でも
  `finally` で必ず解放する（`PtiFinalEngineTest` で検証）。

### 4.1 忠実性テスト（JVM）

ONNX Runtime は Android 版しか依存に無いため、JVM では**モデル出力そのもの**を
テストフィクスチャにして移植の一致を確かめた。

- `work/pianovam_models/export_pti_fixture.py` が PianoVAM #9 の 10〜20秒（実モデル出力
  1,000フレーム × 88鍵 × 4ヘッド、1.4 MB）を
  `app/src/test/resources/pti/pv9_10s.frames.bin` に、Python の復号結果を
  `.json` に書き出す（トリム無し／有りの両方）。
- `PtiPostProcessorTest` は Kotlin の復号結果を Python と**音符単位で比較**
  （音高は完全一致、onset・終端は 1 ms 未満）。トリム無しで 110 音、トリム有りで 110 音
  （うち 6 音が短縮）が一致する。
- 移植前の段階で、Python 側の再実装が公式 `RegressionPostProcessor` と
  **音符完全一致（最大差 0.004 ms）** であることも確認済み（`tune_pti.py` の
  `[fidelity]` 行）。つまり「公式 ≡ Python 再実装 ≡ Kotlin 移植」が数珠つなぎで検証できている。
- `PtiOnnxTranscriberTest` は窓計画・中央50%のステッチ・端の扱い・区間進捗・
  キャンセル・無音をスクリプト化したモデルで検証。
- `PtiFinalEngineTest` はセッションの取得・解放（例外時も解放）、メモリ不足時の拒否、
  音符のマッピングを検証。
- `FinalTranscriberEngineTest` はエンジン差し込み（PTI の音符が楽譜に入る／
  Basic Pitch の 2 秒窓走査が走らない）、`OutOfMemoryError`・セッション生成失敗時の
  フォールバックと理由表示、エンジン無効化を検証。

テストは既存 198 件＋新規 16 件の **217 件すべて通過**（1 件は既存のスキップ）。

## 5. 残る課題と実機での確認点

1. **実機（OPPO / ARM）で 1 本測る**: 40 秒の録音で解析時間（目標 10〜15 秒以内）、
   ピークメモリ、発熱。`MIN_PTI_FREE_MB = 1400` の閾値が実機の空き RAM に対して
   厳しすぎ／緩すぎでないか（緩ければ PTI が動くが OOM リスク、厳しければ常に
   Basic Pitch になる）。
2. **実マイクでのノイズ除去の既定**: 標準と弱を同じ演奏で聴き比べ、和音の欠けと
   ノイズ由来の偽音のバランスで決める。
3. **Offset の残差**: pv60 のような速い減衰では、まだ +240 ms 程度伸びる。
   譜面は16分グリッドに量子化するので実害は小さいが、スタッカートが伸びる。
   改善するならペダル枝を含む完全版モデル（サイズ増）か、減衰の時定数を使う推定。
4. **int8 量子化**: 94 MB → 25 MB 前後に落ちる可能性（未検証）。速度・精度の両方を
   測ってから判断する。実現すれば APK は約 120 MB になり、Play 配布の 200 MB 制限にも余裕ができる。
5. **Play 配布**: 現在の 192 MB はベース APK 上限 200 MB ぎりぎり。配布するなら
   Play Asset Delivery へ PTI を逃がす。

## 6. 再現

```bash
cd work/pianovam_models
python3 tune_pti.py sweep   # パラメータ掃引 + バイアス + 公式一致の確認
python3 tune_pti.py trim    # 減衰トリムの比較
python3 tune_pti.py noise --case white12 --dn weak   # ノイズ×Denoiser（1条件ずつ）
python3 tune_pti.py cost    # 速度・メモリ
python3 export_pti_fixture.py   # JVM テスト用フィクスチャの再生成
python3 tools/fetch_pti_model.py  # 94.1MB の重みを assets へ（SHA-256 検証つき）
```

測定結果は `work/pianovam_models/results/tune-*.json`。
