## 0. この文書の読み方

本書は、Harmono Pianoの採譜体験を参考にしながら、Android専用の独立したネイティブアプリケーション「PianoSheet」を開発するための仕様書である。Harmono Pianoの内部実装を知っていることを前提にせず、外から確認できる挙動と、本アプリで採用する設計を分けて記載する。Webアプリ版・iOS版は本バージョンの開発対象に含めない。

- **[提案]** 実装を成立させるために本書で提案する設計。開発開始時に変更してよい。
- **[要検証]** 技術検証・実機テストで実現可能性や数値を確定する項目。
- **MUST** 必須要件。
- **SHOULD** 原則として実装する要件。合理的な理由があれば変更できる。
- **MAY** 将来対応または任意機能。


## 0.3 v1.2の変更点

- 開発対象をWebアプリからAndroid専用ネイティブアプリへ変更。

- Web Audio API / AudioWorkletをAndroid AudioRecordへ変更。

- 楽譜表示をAndroid Canvas / Compose Canvasによるネイティブ描画へ変更。
- Room / DataStoreを用いた端末内データ管理を追加。
- Androidの権限、Foreground Service、画面回転、発熱・バッテリーへの対応を追加。
- Web版・iOS版は本バージョンの対象外と明記。

# 1. プロジェクト概要

## 1.1 目的

ピアノの演奏音声をマイクまたは音声ファイルから取得し、音声解析によって音符を推定して、編集可能な五線譜を自動生成する。

本プロジェクトで最も重要な特徴は、**録音中に採譜結果を画面へリアルタイム表示すること**である。録音が終わってから初めて楽譜を表示する方式にはしない。

ただし、録音中は処理速度を優先し、音の高さ・発音タイミングの検出を中心にする。四分音符・八分音符などのリズム表記、休符、小節、テンポ、拍子などの整形は、録音終了後の全体再解析で行う。

## 1.2 基本コンセプト

処理を次の2段階に分ける。

1. **Live Transcription（録音中）**
   - 音声を継続取得する。
   - 鳴っている音の高さを検出する。
   - 検出音を大譜表へ順次追加する。
   - 対応する鍵盤を点灯させる。
   - リズム表記は未確定の仮表示とする。
   - 音声入力から画面表示までの遅延目標は1〜2秒。
2. **Final Transcription（録音終了後）**
   - 保存済みの録音全体を再解析する。
   - 音符の開始時刻・終了時刻・長さを推定する。
   - テンポ、拍子、調性、休符、小節、左右の手などを整える。
   - 編集可能な最終楽譜を生成する。

## 1.3 成功条件

- 録音を開始すると、録音中に音符が五線譜へ追加される。
- 目標1〜2秒の遅延で、検出音を画面へ反映できる。
- 同時に鳴った複数音を、可能な限り別々の音符として検出できる。
- 録音中は音符の長さを確定しなくてもよい。
- 録音を停止すると、自動的に最終解析が始まる。
- 最終解析後、通常のピアノ譜として読める楽譜を表示する。
- 最終楽譜を再生・編集・保存・エクスポートできる。

## 1.4 開発対象と非対象

### 初期開発の対象

- ピアノの単独演奏音声
- マイク録音
- 音声ファイルアップロード
- 単音および和音の検出
- ト音記号・ヘ音記号の大譜表
- 録音中のリアルタイム表示
- 録音後の全体再解析
- 楽譜表示、再生、編集、保存、出力

### 初期開発では対象外、または将来対応

- オーケストラや複数楽器が混ざった音源の完全な分離採譜
- 歌声の採譜
- ギター、ドラムなど他楽器の専用譜
- 自動伴奏生成
- 自動作曲
- 楽譜画像（紙の譜面）のOCR
- 高度なペダル記号・演奏表現の完全推定
- 複数ユーザー同時編集

# 2. ユーザー・利用環境

## 2.1 想定ユーザー

- 自分のピアノ演奏を楽譜にしたい人
- 耳コピした演奏を五線譜にしたい人
- 楽譜が存在しない演奏を記録したい人
- 作曲・編曲のアイデアを譜面に残したい人

## 2.2 対応プラットフォーム

**[確定] Android専用アプリとして開発する。**

- Androidスマートフォンを主対象とする。
- Androidタブレットも可能な範囲で対応する。
- iOS・iPadOS・Webブラウザ版・デスクトップ版は本バージョンの開発対象外とする。
- Google Play配布を想定するが、開発中はAPKによる直接インストールも可能にする。

### 2.2.1 Androidバージョン

- 開発開始時点で利用可能なAndroid API・ライブラリの対応状況を確認してminSdkを決定する。
- 初期提案はAndroid 10（API 29）以降。ただし、採用する推論ランタイム・音声API・Foreground Service要件を検証して最終決定する。
- targetSdkはリリース時点のGoogle Play要件に合わせる。

## 2.3 画面サイズ・向き

- スマートフォン縦画面を基本とする。
- 横画面では楽譜と鍵盤を広く表示できるようにする。
- タブレットでは大譜表の表示幅を拡張する。
- 録音・停止ボタンは片手でも操作しやすい位置とサイズにする。
- 画面回転で録音・解析セッションを失わない。
- 画面再生成時はViewModel等から状態を復元する。

## 2.4 ネットワーク・実行モード

- ライブ採譜は原則として端末内で実行し、ネットワーク遅延に依存しない構成を目指す。
- 最終解析は端末内処理を基本候補としつつ、モデルサイズ・処理時間・メモリの検証結果によって、任意の解析サーバーを利用できる設計とする。
- サーバー利用時は、録音データを送信する前に用途・送信先を明示する。
- サーバーに接続できない場合も、録音データを端末内に保持し、再試行できるようにする。

# 3. 画面・操作仕様

## 3.1 画面一覧

| ID | 画面 | 役割 |
|---|---|---|
| SCR-001 | ホーム | 新規録音、音声アップロード、プロジェクト一覧 |
| SCR-002 | ライブ採譜 | 録音中の音符表示、鍵盤点灯、録音操作 |
| SCR-003 | 解析中 | 停止後の最終解析の進捗表示 |
| SCR-004 | 完成楽譜 | 最終楽譜、再生、編集、保存、出力 |
| SCR-005 | 楽譜編集 | 音符・休符・拍子・テンポなどの編集 |
| SCR-006 | エクスポート | PDF・MIDI・MusicXMLなどの出力 |
| SCR-007 | 設定 | 入力デバイス、解析設定、表示設定 |

## 3.2 ホーム画面

### 必須UI

- アプリ名・ロゴ
- 「新しく録音」ボタン
- 「音声ファイルをアップロード」ボタン
- 最近のプロジェクト一覧
- 保存済みプロジェクトを開く操作

### 動作

- 新しく録音を選択すると、マイク権限を要求し、許可されたらライブ採譜画面へ移動する。
- 音声ファイルを選択すると、ファイル検証後に解析を開始する。
- 保存済みプロジェクトを選択すると、完成楽譜または前回の状態を開く。

## 3.3 ライブ採譜画面

### 3.3.1 画面構成

参考動画の操作体験を踏まえ、以下の領域を設ける。

| 領域 | 表示・機能 |
|---|---|
| ヘッダー左 | ホームへ戻る、または録音画面を閉じる |
| ヘッダー中央 | 録音経過時間、検出音符数 |
| ヘッダー右 | マイク状態、音声入力状態、設定 |
| 中央 | ト音記号・ヘ音記号の大譜表と検出音符 |
| 下部 | 録音停止、音声アップロードなどの操作 |
| 最下部 | ピアノ鍵盤。検出された音の鍵盤を強調表示 |

### 3.3.2 録音中に表示する情報

- 録音経過時間（例：00:17）
- 検出した音符イベント数（例：116 notes）
- マイク接続状態
- 現在の音声入力レベルまたは入力状態
- 大譜表上の暫定音符
- 検出中・直近に検出した鍵盤の強調表示
- 解析状態（正常、遅延中、入力なし、エラー）

### 3.3.3 録音中の音符表現

**[確定] 録音中は音程を優先し、音符の長さや四分音符・八分音符などのリズム種類は後から決める。**

- 検出した音高に対応する五線譜上の位置へ音符を表示する。
- 録音中は、音符の長さを確定した標準譜面として表現しなくてよい。
- 暫定表示では、音符の頭（notehead）を中心とした簡易表現を採用する。
- 必要に応じて、仮の音符・薄い色・縁取りなどで「まだ確定していない」ことを表す。
- 音高の綴り（例：C♯ / D♭）は暫定的に決定し、最終解析時に調号・調性を考慮して整える。
- 音符が重なった場合は和音として縦方向に配置する。
- 録音中に画面が右へ伸び、表示領域を超えた場合は自動スクロールする。
- 現在追加されている位置を視認できるようにする。

### 3.3.4 音符カウンター

- 検出した音符イベント数を表示する。
- 1つの和音に3音が含まれる場合、原則として3音として数える。
- 同じ音を押し続けている間、同じイベントをフレームごとに重複カウントしてはならない。
- 同じ鍵盤を再度弾いたことが検出された場合は、新しい発音イベントとして数える。
- 誤検出を取り消した場合、カウンターも整合するように更新する。

### 3.3.5 ピアノ鍵盤表示

- 一般的なピアノ鍵盤を表示する。
- 音高検出中または直近に検出された音に対応する鍵盤を強調表示する。
- 和音の場合は複数鍵盤を同時に強調表示する。
- 強調表示は検出状態に応じて解除する。
- 色だけに依存せず、必要に応じて音名やMIDI番号なども確認できるようにする。
- 鍵盤表示は音高確認用であり、MVPでは画面上の鍵盤をクリックして演奏する機能は必須ではない。

### 3.3.6 録音操作

- 録音開始
- 録音停止
- 一時停止・再開（SHOULD）
- 録音破棄
- 入力デバイス切り替え
- 録音状態の表示

停止を押した場合、録音データを保存してSCR-003へ遷移する。一時停止・再開を実装する場合、停止と一時停止の意味を明確に区別する。

## 3.4 音声アップロード画面・操作

### 3.4.1 対応形式

初期対応候補：

- WAV
- MP3
- M4A
- FLAC
- OGG

実装時にFFmpegなどでデコード可能な形式を確認し、未対応形式は理由を表示して拒否する。

### 3.4.2 初期制限案

- 最大録音時間：10分
- 最大ファイルサイズ：100MB

上記は初期運用の提案値であり、サーバー性能・ストレージ・解析時間を確認して調整できるようにする。

### 3.4.3 アップロード後

- ファイル名、ファイルサイズ、長さを表示する。
- 必要に応じて音声を試聴できるようにする。
- 「解析開始」で最終解析を開始する。
- ファイルの解析中は進捗とキャンセル操作を表示する。

アップロード音声についても、最終解析だけでなく、可能であれば解析過程の音符を順次表示する。ただし、最初のMVPではファイル全体のアップロード完了後に解析してもよい。

## 3.5 解析中画面

### 3.5.1 表示する工程

参考動画では以下の3つの文言が確認できた。

1. `Preparing...`
2. `Writing the notes...`
3. `Finishing up...`

PianoSheetでも3段階の進捗UIを採用する。表示文言は日本語を標準とし、英語表示にも対応可能な構造にする。

### 3.5.2 工程の定義（PianoSheet側の設計）

| 工程 | 表示例 | 実際に行う処理 |
|---|---|---|
| 1 | 準備中... | 録音データの確定、デコード、サンプリングレート統一、波形・解析区間の準備 |
| 2 | 音符を解析中... | 全体音声から音高・発音・消音の推定、リアルタイム仮イベントとの照合 |
| 3 | 楽譜を仕上げています... | 音符の長さ、リズム、休符、小節、テンポ、拍子、調号、左右の手を整え、楽譜データを生成 |

※これはPianoSheetの処理設計であり、Harmono Pianoの内部処理を断定するものではない。

### 3.5.3 進捗表示

- 現在の工程名を表示する。
- 進捗率を表示する。
- 可能な限り実際の処理状況に基づいて進捗を更新する。
- 実際の進捗率が取得できない場合、見せかけの数値を急激に増やさず、工程名と処理中表示を使用する。
- 解析中は二重実行を防止する。
- キャンセル時は、録音データを保持するか破棄するかをユーザーに確認する。
- エラー時は工程と原因を表示し、再試行できるようにする。

## 3.6 完成楽譜画面

### 3.6.1 ヘッダー

- プロジェクト名
- プロジェクト名変更
- 編集（Edit Score）
- エクスポート（Export）
- 保存（Save）
- 閉じる・戻る

### 3.6.2 楽譜表示

- タイトル
- ピアノ大譜表（ト音記号・ヘ音記号）
- 調号
- 拍子記号
- テンポ
- 小節番号
- 小節線
- 音符・休符
- 臨時記号
- タイ・スラーなど、解析・編集で確定できた記号
- 複数段に折り返す通常の楽譜レイアウト

右手・左手の振り分けは自動推定とするが、音域だけで単純に分割すると誤る可能性があるため、音域・音の連続性・同時発音・演奏パターンなどを考慮する。

### 3.6.3 録音中の表示との違い

| 項目 | 録音中 | 完成後 |
|---|---|---|
| 音程 | 暫定検出 | 全体解析で補正 |
| 音符の長さ | 未確定でよい | 推定・確定 |
| 四分音符などの種類 | 表示しない、または仮表示 | 表示する |
| 休符 | 原則未確定 | 推定・配置 |
| 小節 | 連続表示・仮配置 | 拍子に基づいて整形 |
| 調号・臨時記号 | 暫定表記 | 調性を考慮して整理 |
| 右手・左手 | 暫定配置 | 全体を見て再配置 |

### 3.6.4 再生機能

- `Score`：生成した楽譜のMIDI相当データを音源で再生する。
- `Original`：録音した元音声を再生する。
- 再生・一時停止
- シークバー
- 再生速度（例：0.5x、0.75x、1.0x、1.25x、1.5x、2.0x）
- 再生位置と楽譜位置を同期する。
- Score再生時は、現在再生中の小節・音符を強調表示する。
- Original再生時も、可能であれば時間位置に対応する楽譜位置を表示する。

### 3.6.5 追加機能

参考動画で以下の操作項目を確認した。初期MVPでは必須ではないが、画面設計上は拡張できる構造にする。

- `Add to my library to play`：プロジェクトを個人ライブラリに追加する機能。
- `Practice in Piano Roll Mode`：生成した音符をピアノロール形式で表示し、練習に利用する機能。

これらはアカウント・ライブラリ・練習用UIが必要になるため、基本の採譜・楽譜出力が完成した後に実装する。

# 4. リアルタイム採譜仕様（最重要）

## 4.1 ユーザー確定要件

| 項目 | 決定内容 |
|---|---|
| 録音中の表示 | 音程を優先して大譜表へ逐次表示 |
| 解析遅延 | 1〜2秒を目標 |
| 表示方式 | 録音中は横方向に伸びる連続表示、最終楽譜は通常の段組み表示の両方に対応 |
| 録音終了後 | 元音声全体を再解析してリズム・小節などを整える |
| 録音中のリズム | 四分音符・八分音符などを確定しなくてよい |
| 和音 | 複数音の同時検出に対応する |

## 4.2 遅延の定義

「1〜2秒」は、**実際に音が発生してから、その音に対応する暫定音符が画面上に表示されるまで**の時間を指す。

目標値：

- 通常環境：1〜2秒以内を目標とする。
- 受入テスト：基準Android端末・指定音源で、測定した音符イベントの95%が2秒以内に表示されることを目標とする。
- 端末性能・OS状態・推論モデルにより達成できない場合、解析遅延を表示し、音声データを欠落させずに処理する。

この数値は開発目標であり、すべての端末で保証されるものではない。

## 4.4 音声取得

- AndroidのAudioRecordによるマイク入力を使用する。
- AudioRecordで入力デバイスを取得する。
- 音声処理はメインスレッドを塞がない方式を採用する。
- AudioRecordの読み取りを専用スレッドまたは適切な非同期実行コンテキストで行い、音声フレームを継続取得する。
- 内部処理のサンプリングレートはモデル要件に合わせて統一する。
- ステレオ入力は、解析モデルが必要とする場合にモノラルへ変換する。
- 入力音声は最終解析用に原データを保持する。
- 解析用データと保存用データは分離して管理できるようにする。

### 4.4.1 チャンク方式

[提案] 初期実装では、短い音声チャンクを継続的に処理する。

- 取得・送信チャンク：100〜250ms程度を初期検証値とする。
- 解析窓：500〜1000ms程度を初期検証値とする。
- 前後のチャンクを一部重複させ、境界で音符が切れる問題を減らす。
- 上記数値は固定仕様ではなく、遅延・認識精度・通信量を測定して調整する。

## 4.5 ライブ音高検出

Live Transcriptionでは、音符の長さの確定よりも、鳴っている音の高さを素早く認識することを優先する。

検出したい情報：

| 情報 | 説明 |
|---|---|
| Pitch / MIDI Note | 音高。MIDIノート番号で保持 |
| Onset | 音が始まったと推定する時刻 |
| Confidence | 検出の信頼度 |
| Active State | 現在鳴っていると推定されるか |
| Source Chunk | どの音声区間から検出したか |

音符の終了時刻・正式な長さはライブ段階で確定しなくてよい。検出器内部で音の継続状態を追跡してもよいが、楽譜上の四分音符などの表記は最終解析まで保留する。

## 4.6 ポリフォニック（和音）検出

- 同時に複数の音が鳴った場合、各音を独立したPitch候補として扱う。
- 単音専用の検出器だけで完成させない。
- 倍音を別の音として誤検出する可能性があるため、信頼度・音域・時間的継続性を利用して候補を整理する。
- 和音の構成音を同じ時刻付近のイベントとしてグループ化できるようにする。
- 同じ音が長く鳴り続けている場合、毎フレーム新しい音符を作成してはならない。
- 同じ鍵盤が再度打鍵された場合は、再発音として新しいイベントにする。

## 4.7 イベント統合・重複排除

チャンクの重複区間により、同じ発音が複数回検出される可能性がある。

そのため以下を実施する。

1. 音高・開始時刻・継続状態を用いて同一候補を照合する。
2. 既存イベントに十分近い候補は重複として統合する。
3. 同じ音高でも、明確な再打鍵が検出された場合は別イベントとする。
4. 解析済み区間の情報を保持し、チャンクごとの再処理で音符が増殖しないようにする。
5. 低信頼度イベントは即時確定せず、短い保留時間を置いてから表示する方法を検討する。

## 4.8 暫定音符の状態管理

ノートイベントは少なくとも以下の状態を持つ。

- `pending`：検出候補。まだ表示を確定していない。
- `provisional`：ライブ譜面に表示済み。最終解析で変更される可能性がある。
- `confirmed`：最終解析後に確定した。
- `revised`：最終解析で音高・時刻・長さなどが修正された。
- `rejected`：誤検出として除外された。

画面では暫定音符と確定音符を視覚的に区別する。

## 4.9 ライブ譜面の配置

- 五線譜の縦位置はMIDI音高から決定する。
- 横位置は基本的に発音時刻の順番で決める。
- 録音中は正式な小節幅・音符長さを前提にしない。
- 音符の増加に応じて譜面表示領域を右へ拡張する。
- 表示領域を超えると自動スクロールする。
- 現在の追記位置を視認できるようにする。
- 一度表示した暫定音符が最終解析前に変更される場合、対応するイベントIDを用いて更新する。

## 4.10 リアルタイム鍵盤表示

- ライブ検出イベントと鍵盤表示を同期する。
- 検出音を紫系の色などで強調する（色はデザイン設定で変更可能）。
- 複数音同時検出時は複数鍵盤を同時に強調する。
- 音の検出が終了したら強調表示を解除する。
- 表示のちらつきを抑えるため、短い時間の安定化処理を入れる。

## 4.11 遅延・性能対策

- 音声取得処理とUI描画処理を分離する。
- 解析サービスの処理待ちが増えた場合に、未処理チャンク数を監視する。
- 古い解析結果が新しい結果を上書きしないよう、時刻・シーケンス番号を付ける。
- 遅延が目標を超えた場合、UIに警告を表示する。
- 音声を欠落させずに、解析頻度やウィンドウ長を調整できる設計にする。
- UIの描画は音声サンプリングごとに実行せず、まとめて反映する。
- モデル推論は専用Executor / Coroutine Dispatcher / ネイティブ推論スレッドなどに分離する。

## 4.12 音声ファイルのリアルタイム風プレビュー

Android端末から音声ファイルを読み込む場合は、録音と異なり、音声全体が既に存在する。

- ファイルを読み込む。
- 解析を一定区間ずつ進める。
- 解析済み区間の音符を画面へ順次追加する。
- 必要に応じて元音声の再生位置と解析位置を同期させる。

ただし、ファイル解析では録音と同じ1〜2秒遅延を必須としない。処理時間と表示の滑らかさを優先する。

# 5. 録音終了後の最終解析仕様

## 5.1 基本方針

録音終了後は、録音中に蓄積した元音声全体を使って、最初から再解析する。

録音中のイベントをそのまま最終楽譜にするのではなく、暫定結果として利用しながら、最終解析結果で補正する。

## 5.2 最終解析で推定する情報

| 項目 | 処理 |
|---|---|
| 音高 | ライブ検出結果を照合し、誤りを補正 |
| 発音時刻 | より精密に推定 |
| 消音時刻 | 音の終了・減衰を推定 |
| 音符の長さ | 発音・消音・ペダル・残響を考慮して推定 |
| テンポ | 拍の周期を推定 |
| 拍子 | 拍のまとまりから候補を推定 |
| 調性 | 音の出現傾向から候補を推定 |
| リズム | 四分音符、八分音符、付点などへ整理 |
| 休符 | 音のない区間から推定 |
| 小節 | 拍子・テンポを基に分割 |
| 右手・左手 | 音域や声部の連続性などから振り分け |
| 臨時記号 | 調号と音符の綴りを考慮して整理 |

## 5.3 リズム量子化

- 検出時刻をそのまま残す「演奏時刻重視」モードを用意する。
- 拍に近い時刻へ補正する「譜面読みやすさ重視」モードを用意する。
- 量子化の強さを設定できるようにすることを推奨する。
- 強制的にすべての音を拍へ合わせない。
- 速い演奏、ルバート、揺れのある演奏を不自然に均等化しない。

## 5.4 音符の長さとピアノの減衰

ピアノ音は鍵盤を離した後も弦や響きが残るため、録音上の音量が残っている時間と、演奏上の音符の長さは一致しない場合がある。

- 音量が小さくなるまでの全時間を、そのまま音符の長さにしない。
- 発音・減衰パターンをモデルで推定する。
- ペダル使用時は複数音が重なる可能性があることを考慮する。
- ペダル情報が直接取得できない場合、推定の不確かさを許容する。
- 最終楽譜をユーザーが編集できるようにする。

## 5.5 右手・左手の振り分け

- 基本的にト音記号とヘ音記号の大譜表を使用する。
- 単純な固定MIDI番号だけで右手・左手を分割しない。
- 音域、連続した旋律、同時発音、声部の動きを考慮する。
- 同じ音域に両手が入る場合もあるため、誤りを修正できるようにする。
- ユーザーが音符を別の譜表へ移動できるようにする。

## 5.6 調号・拍子・テンポ

- 調性・拍子・テンポは推定結果として扱う。
- 推定に自信がない場合は、確定せず候補や初期値を提示する。
- ユーザーが手動で変更できるようにする。
- 動画に登場した特定のテンポ・拍子を固定値として使用しない。

## 5.7 最終解析後の整合性

- ライブイベントと最終イベントを照合する。
- 最終解析で追加・削除・変更された音符を適切に反映する。
- 暫定音符IDと最終音符IDの対応関係を履歴として保持する。
- 最終楽譜が保存されるまで元音声と暫定結果を保持する。
- 再解析を行っても、ユーザーの手動編集が無断で消えないようにする。

## 9.3 実行配置の基本方針

**端末内ライブ推論を第一候補とする理由:** 目標遅延が1〜2秒であり、録音中の音声を毎回サーバーへ送ると、ネットワーク品質・往復遅延・サーバー負荷に表示速度が左右されるため。Android端末内での推論精度・速度・発熱・メモリをPhase 0で実測し、実用に届かない場合にのみサーバー推論を代替案として採用する。



- マイク取得と録音データの一時保存はAndroid端末内で行う。
- ライブ音高検出は端末内推論を第一候補とする。
- ライブ検出結果をCompose UIへ直接渡さず、Repository / StateFlow等の状態管理層を介す。
- 最終解析は端末内・任意サーバーのどちらにも差し替えられるインターフェースにする。
- サーバーを使う場合でも、ライブ表示のために常時音声を送信する設計を初期要件にしない。
- サーバー接続が失敗しても録音データを失わない。

## 9.3 リアルタイムエンジンと最終解析エンジンを分ける

**必須設計方針:** Live TranscriptionとFinal Transcriptionを別のインターフェースとして実装する。

理由：

- ライブ側は遅延を最優先する。
- 最終解析側は精度と音楽的整合性を優先する。
- ライブ用モデルを交換しても最終楽譜生成を壊さない。
- 最終解析モデルを交換してもライブUIを壊さない。

インターフェース例：

```python
class LiveTranscriber:
    def start_session(self, config): ...
    def push_audio_chunk(self, chunk, sequence, timestamp): ...
    def get_note_events(self): ...
    def finish_session(self): ...

class FinalTranscriber:
    def transcribe(self, audio_file, options): ...

class ScoreBuilder:
    def build(self, note_events, score_options): ...
```

上記は構造例であり、実際の型・戻り値は実装時に定義する。

## 9.4 AI・採譜モデル選定

### 9.4.1 Androidでのモデル実行方針

- ライブ推論モデルはAndroid端末内で実行できる形式を優先する。
- TensorFlow Lite / LiteRTまたはONNX Runtime Mobileで実行可能か、モデル変換・演算子対応・量子化後の精度を検証する。
- Python向けモデルが存在することだけを理由に、Androidでそのまま動作すると判断してはならない。
- モデル変換が困難な場合は、C++ NDKでの推論、専用の軽量モデル、または任意サーバー推論を比較する。
- 端末内推論を採用する場合、対応端末の最低性能・RAM・発熱・バッテリー消費を実機で測定する。

### 9.4.2 Spotify Basic Pitch

- ポリフォニック音源に対応する自動採譜候補。
- 複数楽器に汎用的だが、単一楽器の録音で最もよく機能する旨が公式説明にある。
- 軽量な候補として、最終解析のベースラインに利用する。
- Apache License 2.0とされているため、導入時は実際の配布物・依存物のライセンスも確認する。
- **注意:** 公式説明だけでは本プロジェクトの1〜2秒のストリーミング要件を満たすと判断できない。チャンク処理での遅延・境界誤検出・和音精度を必ず検証する。

### 9.4.3 Magenta Onsets and Frames

- ピアノ演奏の音声から音符を推定するモデルとして知られる。
- 公式資料にはマイク録音による転写例がある。
- ただし、Magentaの該当リポジトリは現在inactiveと記載され、現在の作業についてMT3を参照するよう案内されている。
- そのため、既定の本番依存先に即決せず、比較検証用候補として扱う。

### 9.4.4 モデル採用ルール

モデル名だけで採用を決めない。以下の評価音源でテストする。

- 単音
- 右手メロディー
- 左手伴奏
- 三和音・四和音
- 両手演奏
- 速い連続音
- 同じ音の連打
- ペダルを使った演奏
- スマートフォンのマイク録音

評価項目：

- 音高正解率
- 発音時刻の誤差
- 同時発音の検出数
- 倍音誤検出数
- 1イベントあたりの表示遅延
- CPU・メモリ使用量
- 長時間実行時の安定性

### 9.4.5 モデルの抽象化

モデルを直接UIから呼び出さない。モデルアダプターを用意し、モデルの入力・出力形式を共通化する。

```text
LiveTranscriber Interface
  ├── Model Adapter A
  ├── Model Adapter B
  └── Experimental Pitch Detector

FinalTranscriber Interface
  ├── Basic Pitch Adapter
  ├── Piano-specific Model Adapter
  └── Future Model Adapter
```

## 9.5 楽譜レンダリング

- ライブ譜面はAndroid CanvasまたはJetpack Compose Canvasで描画する。
- 暫定ノートの追加・更新を局所的に反映し、全画面を毎回再描画しない。
- 完成譜もネイティブ描画を基本とし、MusicXMLを内部スコアモデルへ変換して表示する。
- MusicXMLの読み書きは専用パーサー・変換層に分離する。
- 大譜表、加線、臨時記号、和音、連桁、休符、小節線、複数段の折り返しに対応する。
- 横スクロール・ピンチズーム・ページ表示を検討する。
- 完成譜の再描画でスクロール位置が不用意に戻らないようにする。
- 既存のAndroid対応楽譜描画ライブラリを採用する場合、ライセンス・保守状況・MusicXML対応範囲を確認する。

## 9.6 Androidライフサイクル・録音サービス

- 録音状態はActivityやCompose画面の寿命に依存させない。
- 画面回転・画面遷移で録音セッションが二重開始されないようにする。
- 画面消灯中も録音を継続する要件を実装する場合、AndroidのForeground Serviceとマイク利用に関する最新のOS制限を遵守する。
- 録音中は通知領域に録音中であることと停止操作を表示する。
- ユーザーが停止した場合、サービス・AudioRecord・バッファを確実に解放する。
- OSによりプロセスが終了した場合に備え、録音データを短い間隔で永続化する。
- バックグラウンド録音を実装しないMVP段階では、画面内録音に限定することを明示する。

# 11. アプリ内部インターフェース・サーバー通信設計

## 11.1 Android内部の主要インターフェース

アプリ内の主要機能を以下の責務に分ける。

| インターフェース | 責務 |
|---|---|
| AudioCaptureManager | AudioRecordの開始・停止・入力状態管理 |
| RecordingRepository | 元音声の保存・録音メタデータ管理 |
| LiveTranscriber | 音声チャンクからライブ音符イベントを生成 |
| NoteEventRepository | 暫定イベントの統合・重複排除・永続化 |
| FinalTranscriber | 録音全体から最終音符を推定 |

| ScoreRepository | 楽譜・編集履歴の保存 |
| ExportManager | PDF・MIDI・MusicXML出力 |
| PlaybackManager | Score / Original再生と同期 |

## 11.2 任意の最終解析サーバーAPI

サーバー側の最終解析を利用する場合に限り、以下のAPIを実装する。

| Method | Endpoint | 内容 |
|---|---|---|
| POST | `/api/v1/transcriptions` | 最終解析ジョブ作成・音声登録 |
| GET | `/api/v1/jobs/{job_id}` | 解析状態取得 |
| GET | `/api/v1/transcriptions/{id}/score` | 最終楽譜取得 |
| POST | `/api/v1/transcriptions/{id}/exports` | 出力ファイル生成 |
| GET | `/api/v1/exports/{export_id}` | 出力ファイル取得 |

サーバー利用はAndroidアプリの動作に必須としない構成を目指す。サーバーへ送信する場合は、送信前にユーザーへ明示する。

## 11.3 サーバー通信

- HTTPSを必須とする。
- 長時間の最終解析はジョブ方式とする。
- 進捗取得はポーリングまたはServer-Sent Events等を比較する。
- ライブ採譜の音声ストリーミングをサーバーへ送る方式は、端末内推論で目標精度が出ない場合の代替案として検証する。
- サーバー通信が失敗しても、元音声とローカル暫定イベントを保持する。

## 11.4 エラー応答

- マイク権限が拒否された。
- マイクが存在しない、または他アプリが占有している。
- AudioRecord初期化失敗。
- 対応外の音声形式。
- ファイルサイズ・時間超過。
- 音声デコード失敗。
- AIモデルロード失敗。
- メモリ不足・推論タイムアウト。
- サーバー接続失敗。
- 保存失敗。
- エクスポート失敗。

エラーコードとユーザー向けメッセージを分け、再試行可能なエラーには再試行操作を提供する。

# 12. 非機能要件

## 12.1 パフォーマンス

- ライブ表示の遅延目標は1〜2秒。
- UIスレッドを長時間ブロックしない。
- 音声を録音中に継続保存できる。
- 長時間録音でもメモリ使用量が無制限に増えない。
- 解析チャンクの待ち行列を監視する。
- 完成譜が長くてもスクロール・描画を継続できる。

## 12.2 安定性

- 録音中の通信切断に備え、クライアント側に一時バッファを保持する。
- 再接続時にセッション状態を復元できるようにする。
- 解析失敗時も元音声を保持する。
- 最終解析を再実行できるようにする。
- 保存前の編集内容が不用意に消えないようにする。

## 12.3 プライバシー・セキュリティ

- マイクはユーザー操作後にのみ取得する。
- マイク利用中であることを明確に表示する。
- 音声ファイルの実体・MIMEタイプを検証する。
- アップロードサイズ・時間に制限を設ける。
- ファイル名をそのまま保存パスとして使用しない。
- 保存先パスをユーザーから直接指定できないようにする。
- HTTPSを使用する。
- 音声データを無断で外部サービスへ送信しない。
- 音声をAI学習に利用する場合は明示的な同意を取る。
- 一時ファイルを不要になった時点で削除する。
- プロジェクト削除時に関連音声・解析データ・出力データも整理する。

## 12.4 Android固有要件

- マイク権限は録音開始時など必要なタイミングで要求する。
- 録音中であることを画面内および必要に応じて通知領域で明示する。
- OSバージョンごとのマイク・Foreground Service制限に従う。
- バッテリー最適化・省電力モードによる推論性能低下を考慮する。
- 端末の発熱・メモリ不足を監視し、必要なら解析負荷を下げる。
- 端末内に保存する音声・プロジェクトの削除機能を提供する。
- AndroidのStorage Access Frameworkを利用し、ユーザーが保存先を選べるようにする。
- 端末内モデルの更新・差し替え時にモデルのバージョンを記録する。

## 12.5 アクセシビリティ

- 録音状態を色だけで表さない。
- ボタンに明確なラベルを付ける。
- キーボード操作にも可能な範囲で対応する。
- 音符の信頼度を色以外の方法でも確認できるようにする。
- 小さい画面でも録音停止ボタンを操作しやすくする。

# 16. 実装時の重要な注意事項

1. **ライブ解析で完成した譜面を作ろうとしない。** 録音中は音高を優先し、リズムは後処理に回す。
2. **1〜2秒の遅延を最初から測定する。** 実装後に初めて計測するのではなく、Phase 0でモデルと処理方式を比較する。
3. **単音検出だけで完了にしない。** ピアノは和音を弾くため、ポリフォニック検出が必須。
4. **チャンク重複による二重登録を防ぐ。** 同じ音符を何度も画面へ追加しない。
5. **元音声を必ず保持する。** ライブ検出結果が誤っていても、最終解析でやり直せるようにする。
6. **ライブ用と最終用のAIモデルを分けられるようにする。** それぞれ必要な性能が異なる。
7. **音の余韻を音符の長さと誤認しない。** ピアノの減衰・ペダル・残響を考慮する。
8. **調号・拍子・テンポを根拠なく固定しない。** 推定値として扱い、ユーザーが修正できるようにする。
9. **再解析で手動編集を消さない。** 編集履歴とリビジョンを管理する。
10. **UIをAIモデルに依存させない。** 共通イベント形式を介してモデルを差し替えられるようにする。
11. **Harmono Pianoのブランド・ロゴ・独自素材を流用しない。** 操作体験を参考にしつつ、PianoSheet独自のデザインと実装にする。
12. **ライブラリのライセンス・モデルの利用条件を確認する。** ソースコードのライセンスだけでなく、学習済みモデル・依存ライブラリ・音源データの条件も確認する。

# 17. 最終完成条件

以下をすべて満たしたとき、PianoSheetの基本完成とする。

- [ ] マイクでピアノを録音できる。

- [ ] 音符が1〜2秒を目標に大譜表へ追加される。

# 19. 開発担当AIへの指示

この仕様書をプロジェクトの基本要件として扱う。

実装を開始する前に、まず既存リポジトリ・Android開発環境・依存関係・実機またはエミュレーターを確認し、現状を壊さない計画を作成すること。

**プラットフォーム制約:** 本プロジェクトのユーザー向けアプリはAndroid専用である。Next.js / ReactによるWebフロントエンド、ブラウザUI、iOSアプリを作成してはならない。KotlinとJetpack Composeを基本とする。Python/FastAPIは、最終解析を端末外で実行する必要があると技術検証で判断された場合に限る任意のバックエンドであり、Webアプリではない。

実装順序は次の通りとする。

1. Phase 0の技術検証を実施し、リアルタイム1〜2秒の実現可能性を検証する。
2. 採用するLiveTranscriberとFinalTranscriberの構成を決定する。
3. 共通ノートイベント形式を定義する。
4. AudioRecord・端末内推論・ライブ譜面表示を実装する。
5. 録音後の再解析・楽譜生成を実装する。
6. 編集・再生・エクスポートを実装する。
7. 受入テストを実施し、性能・認識精度を記録する。

**重要:** 最初から全機能を一括実装しない。各Phaseの完了条件を満たしてから次へ進む。ただし、リアルタイム採譜は本アプリの中心機能なので、後回しにせずMVPの段階で実装する。
