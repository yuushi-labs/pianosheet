# Phase 2.1 修正レポート（実機フィードバック対応）

2026-11-17。実機で Phase 2 APK を試した録画（SCR-002 ライブ譜面 / SCR-004 完成楽譜）から、
次の5点を修正した。録音そのものは無加工のまま、解析用コピーと表示だけを変えている。

## 1. ダークモードで楽譜が見えない

**症状**: 背景 `#141218` に対し、五線・ト音/ヘ音記号・調号・拍子・符頭・符尾・連桁・臨時記号が
すべて黒（`0xFF1B1A1D` 等のハードコード）で描かれ、休符以外ほぼ読めなかった。

**修正**: `ui/theme/ScorePalette.kt` を新設し、`MaterialTheme.colorScheme` から配色を作る。

| 用途 | 色 |
|---|---|
| 符頭・符尾・連桁・記号・臨時記号・調号・拍子 | `onSurface` |
| 五線・小節線・加線 | `onSurfaceVariant` × 0.65 |
| 小節番号・音名ラベル | `onSurfaceVariant` × 0.80 |
| 再生中の音符・最新音符・再生ヘッド | `primary` |
| 演奏中の小節の帯 | `primary` × 0.12 |

`ensureContrast()` が WCAG コントラストを計算し、スキーム側が薄すぎる場合は目標値
（音符 7:1、五線 3:1、アクセント 4.5:1）まで寄せる。`ScorePaletteTest` がライト/ダーク両方で
この下限を検査する（旧来の黒は `#141218` 上で 1.02:1 しかないこともテストで固定）。
`CompletedScoreCanvas` / `StaffCanvas` はすべて `rememberScorePalette()` 経由で描く。

## 2. 速度チップ `1.5x` が右端で潰れる

**症状**: 720px 幅で「速度 0.5x 0.75x 1.0x 1.25x」の後ろに `1.5x` が縦長の枠として押し潰されていた。

**修正**: チップを `FilterChip` から幅30dpのコンパクトな `Surface` チップにし、`FlowRow`
（`weight(1f)`）に並べた。収まらない端末では2行目に折り返す（押し潰されない）。
ラベルは `SpeedOptions.label()` が生成し、常に5文字以内（`0.5x`, `0.75x`, `1.0x`, `1.25x`, `1.5x`）。

## 3. 3.2kHz 級の定常狭帯域ノイズ

**症状**: 録音区間に非常に狭い（<1Hz）定常ピークが乗り、高音域の誤検出の温床になっていた。

**修正**: `core/dsp/ToneNoiseDetector.kt` を追加。

- 各フレームで「局所中央値（31ビン）の3倍以上」のビンを tonal と数え、
  その出現率が **0.80 以上**、かつ平均スペクトルで肩（±4〜20ビン）より **15dB 以上**突出したピークを
  定常トーンとして検出（1.2〜8kHz、最大3本、放物線補間で周波数決定）。
- 抑圧はディープなIIRノッチではなく **STFTゲイン**で行う（中心±2ビン＝±43Hzを −18dB）。
  `Denoiser`（最終解析）と `StreamingDenoiser`（ライブ）の両方に効く。
- ライブは `ToneNoiseTracker` が約0.5秒で確定し、以降のチャンクに適用する。
- しきい値を高めにしたのは実測から: きれいなピアノ録音（Für Elise）でも「70%のフレームで突出する
  ビン」は存在し（同じ音の繰り返し）、それをノッチすると本物の音を削ってしまう。

**注意（実測）**: 今回のユーザー録音（動画から抽出した音声）の 3.2kHz ピークは、
無音区間では消えていてピアノの音量と連動していた。つまり動画音声では「音楽の一部」に見える。
そのため自動ノッチはこの録音では発動せず（`stationary tones: []`）、採譜の改善は主に 4・5 による。
本当に連続する電子音（充電器の唸り等）では発動する。`ToneNoiseDetectorTest` が合成信号で
「3210Hz の定常音は −12dB 以上落ち、ピアノの 261/523/785Hz は ±2dB 以内」を検査している。

## 4. 高音・倍音ゴーストの抑制

`core/inference/NoteCandidateFilter.kt`（窓ごと）と `FinalNoteMerger.suppressGhosts()`（統合後）:

| 規則 | しきい値 |
|---|---|
| 打鍵でない（減衰尾の再報告） | onset strength < 0.20 |
| クリック | 長さ < 80ms |
| 高音域（MIDI ≥ 84 = C6以上） | onset ≥ 0.40、長さ ≥ 100ms、confidence ≥ 0.25 |
| 倍音ゴースト | 同時（±60ms）の強い下の音（confidence ≥ 0.35）に対し オクターブ/12度/2オクターブ/短10度/長10度/3オクターブ上で、confidence が 0.55倍未満 |

さらに `FinalNoteMerger` の統合条件に「同じ音高で、前の音の前半に始まる検出は同じ音」を追加
（窓がずれて 100ms 前後ずれた重複を1つにまとめる）。

## 5. テンポが倍（160 BPM）に飛ぶ

`domain/final/TempoEstimator.kt`:

- **アタックのクラスタリング**: 90ms 以内の発音を1つの鍵盤操作にまとめる（和音・分割音）。
  強さの重みは合算（上限3.0）。
- **テンポ選好**: 候補周期の位相ヒストグラム得点に、100 BPM を中心とした対数正規の重み
  （σ=0.9オクターブ）を掛ける。95 と 190 が同じだけ説明できるなら 95 が選ばれる。

## 実測（この修正前 → 後）

ユーザーの録音（デバッグ動画 5–30s、22.05kHz モノラル化）を `verify_real_piece.py` で解析:

| | 修正前 | 修正後 |
|---|---|---|
| 音符数（最終解析） | 287（実機）／247（動画音声の再現） | 213 |
| テンポ | 160 BPM | **101.85 BPM** |
| 拍子 | 2/4 | 4/4 |
| 調 | 嬰ハ長調（7♯） | 嬰ハ長調（7♯、変化なし） |
| MIDI ≥ 84 の音符 | 36 | 3 |

実演奏での検証（Wikimedia Commons, CC BY-SA の実録音）:

| 曲 | テンポ | 拍子 | 調 | 音符 | 冒頭の採譜 |
|---|---|---|---|---|---|
| Für Elise（学生演奏・45秒） | 109 BPM | 4/4（原曲 3/8） | 4♯ 長調（原曲 イ短調） | 245 | `E5 D#5 E5 D#5 E5 B4 D5 C5` = **原曲どおり** |
| Gymnopédie No.1（45秒） | 77 BPM | **3/4** | **ニ長調（2♯）** | 147 | `G2 B3 D4 D5 F#4 …` = 冒頭の G(maj7) 和音どおり |

わかったこと:

- 旋律・和音・テンポ・（Gymnopédie では）拍子と調まで一致する。
- **調判定は Für Elise で外す**（ホ短調寄りの内容ではなく、サビの E が全体の41%を占めるため
  E 長調と判定）。抜粋がE偏重なので Krumhansl プロファイルでは E が勝つ。原曲の譜面は
  調号なし（イ短調）なので、ここは既知の限界として残す。
- 拍子候補に 3/8 が無いため Für Elise は 4/4 になる（仕様 §5.2 の候補は 4/4・3/4・2/4・6/8）。

## 再現手順

```bash
python3 phase0-poc/scripts/verify_real_piece.py --wav <22.05kHz mono wav> --name fur-elise \
    --out app/src/test/resources/real-takes/fur-elise.csv
./gradlew :app:testDebugUnitTest --tests "*RealTakeAnalysisTest"
```

`RealTakeAnalysisTest` は CSV（ONNX 推論結果）を `NoteCandidateFilter` → `FinalNoteMerger` →
`ScoreBuilder` に通すので、推論以外はアプリ本体のコードがそのまま検証される。
