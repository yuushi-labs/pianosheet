## 0. 結論（要約）

| 問い | 結論 |
|---|---|
| 録音中に1〜2秒以内で音符を出せるか | **達成できる**。Basic Pitch ONNX を「2.0秒窓・0.25秒ステップ」で回すと、音の発生から表示までの**中央値 377 ms / p95 552 ms**（全イベントが2秒以内）。 |
| 和音を複数音として拾えるか | **拾える**。3音和音 F1 1.000、4音和音 F1 0.923（ライブ処理の基準設定）／信頼度下限0.45で 1.000。 |
| 同じ音の保持で増殖しないか | **増殖しない**。T-002（3秒保持）F1 1.000、イベント1個のみ。 |
| 同じ音の連打を別イベントにできるか | **できる**。T-003（280ms間隔×8回）F1 1.000。ただし Basic Pitch の生の onset 活性で減衰尾を弾く判定（後述 §5）が必須。 |
| チャンク境界の重複・欠落は制御できるか | **制御できる**。3つ目の工夫（確定済み区間の除外＋保留＋統合）で、モデルが返す候補2,585個から実イベント234個に整理（削減率 91%）。 |
| 端末内推論は現実的か | **現実的**。モデルは **230 KB**、2秒窓の推論は本検証機で 23 ms（2スレッド）/ 35 ms（1スレッド）。1コアでも1秒分の音声を35msで処理できる。 |
| Phase 1 に進めるか | **進める**。採用構成は §8 のとおり。 |

一方で、**ペダル（残響）と速いパッセージは未達**（§7）。これは Phase 2 の最終解析側で扱う設計にした。

## 1. 検証環境

`phase0-poc/run_phase0.py` の `env` セクションから自動記録。

| 項目 | 値 |
|---|---|
| OS / CPU | Linux x86_64 / 2 vCPU |
| メモリ | 1,486 MB |
| Python | 3.12.16 |
| NumPy | 2.5.4 |
| onnxruntime | 1.31.1（CPUExecutionProvider） |
| モデル | Basic Pitch ICASSP 2022 ONNX |
| モデルサイズ / SHA-256 | 230,444 bytes / `2c3c1d144bfa61ad236e92e169c13535c880469a12a047d4e73451f2c059a0ec` |

### 1.1 basic-pitch を「インストールせず」に使った理由

`pip install basic-pitch`（0.4.0）は **TensorFlow を `<2.15.1` に固定**しており、この環境の Python 3.12 には適合するホイールが存在しない。さらに note 生成部が librosa / mir_eval / resampy / pretty_midi に依存する。

そこで、

1. PyPI のホイールから**公式の ONNX モデルだけを取り出す**（`scripts/fetch_basic_pitch_model.py`、SHA-256で上流と一致を検証）
2. `basic_pitch/inference.py` と `basic_pitch/note_creation.py` の**前処理・復号処理を numpy/scipy に移植**（`pianosheet_poc/basicpitch_onnx.py`、Apache-2.0、出典明記）

という形にした。モデル自体は無改変で、閾値・melodia トリックも上流と同じ値を既定にしている。これにより「Python 3.12 でも Basic Pitch の推論と復号が動く」ことまで確認できた（Phase 1 の Kotlin 実装でも同じ手順を踏める）。

### 1.2 モデルの入出力（グラフから実測）

```
input   serving_default_input_2:0   (batch, 43844, 1)    float32   2秒 - 1ホップ @22.05kHz
output  StatefulPartitionedCall:1   (batch, 172, 88)     note 活性（88鍵）
output  StatefulPartitionedCall:2   (batch, 172, 88)     onset 活性（88鍵）
output  StatefulPartitionedCall:0   (batch, 172, 264)    pitch contour（3ビン/半音）
```

172フレーム / 2秒 = **86 fps（11.6 ms / フレーム）**、88鍵 = MIDI 21〜108。
出力フレームと入力音声の対応は、単音を既知の時刻に置いたテストで **誤差 0 フレーム**（フレーム * 11.6 ms = 発音時刻）を確認した。

### 1.3 移植時に見つけた落とし穴（記録）

- 2秒窓を0.35秒オーバーラップで並べるとき、各窓の出力から**前後15フレームずつ**を捨てる必要がある。連結後の配列の先頭・末尾だけを削ると、2窓目以降が**1窓あたり約350 msずれる**（最初の実装でこの症状が出て、単音テストで原因を特定した）。
- 44.1kHz の WAV を 22.05kHz に落とす処理はポリフェーズ（`scipy.signal.resample_poly`）で行い、遅延特性を含めて計測に含めた。

## 3. 評価方法（phase0-poc/metrics.py）

- 音高が一致し、発音時刻の差が **±50 ms** 以内のものを正解（TP）として1対1で貪欲マッチ
- Precision = TP / 検出数、Recall = TP / 正解数、F1 はその調和平均
- 発音時刻の誤差（MAE・中央値・p90）、終止時刻の誤差も記録
- 全テストの合計からマイクロ平均を算出（テスト間の重みを音符数で揃えるため）

## 5. 実測2: 減衰尾の再検出の正体と対策（重要な発見）

偽音符の正体を調べるため、Basic Pitch の復号に**モデルの生の onset 活性**（inferred onset を混ぜる前の値）を記録させた。

| イベント | ピッチ | 生 onset 活性 | フレーム活性平均 |
|---|---|---|---|
| T-002 3.6s（実際の打鍵） | G4 | **0.98** | 0.78 |
| T-002 6.56s（減衰尾の分割） | G4 | **0.02** | 0.61 |
| T-005 4.34s（実際の和音） | C4/A3/F3 | **0.94〜0.95** | 0.72〜0.75 |
| T-005 6.56s（和音の残響） | 5音 | **0.02〜0.06** | 0.36〜0.56 |

つまり **「打鍵したか」は生の onset 活性で明確に分離できる**（実打鍵 0.94〜0.98 / 残響 0.02〜0.06）。そこで復号結果に `onset_strength` として保持し、0.30 未満を捨てる（保留する）ルールを入れた。

効果（全体解析のF1）:

| テスト | そのまま | onset強度 ≥ 0.3 |
|---|---|---|
| T-004 上行 | 0.778 | 0.824 |
| T-004b 下行 | 0.571 | 0.600 |
| T-014 ノイズ入り | 0.960 | **1.000** |
| T-012 ペダル | 0.600 | 0.649 |
| マイクロ | P 0.778 / R 0.937 / F1 0.850 | **P 0.796 / R 0.937 / F1 0.861** |

全体解析では控えめだが、**ライブ処理では効果が大きい**。窓ごとに同じ残響を何度も復号するため、偽音符が積み上がるからで、マイクロ F1 が **0.873 → 0.901** に上がり、T-002（保持）/ T-003（連打）/ T-005 / T-006 / T-007 / T-014 が**すべて F1 1.000** になった（T-003 は 0.286 → 1.000）。

> 仕様書 4.7.5「低信頼度イベントは即時確定せず、短い保留時間を置いてから表示する」は、この `onset_strength` を基準にするのが最も筋が良い。Phase 1 の `NoteEventRepository` にこの基準を入れる。

## 6. 実測3: DSPベースラインとの比較

「モデルを使わずに、スマホのDSPだけでどこまで行けるか」を同じ音源・同じ採点で測った。

| 検出器 | 方式 | マイクロF1 | P | R |
|---|---|---|---|---|
| スペクトルピーク（全体解析） | STFTピーク＋パラボリック補間＋倍音除去＋立ち上がり検出 | **0.943** | 0.959 | 0.927 |
| スペクトルピーク（1.5秒窓・0.25秒ステップ） | 同上をストリーム実行 | **0.937** | 0.948 | 0.927 |
| 倍音辞書NMF（全体解析） | KL-NMF（88鍵×倍音テンプレート） | 0.162 | 0.103 | 0.384 |
| Basic Pitch（全体解析） | ICASSP 2022 ONNX | 0.850 | 0.778 | 0.937 |
| Basic Pitch（ライブ処理） | 2.0秒窓・0.25秒ステップ | 0.901 | 0.876 | 0.928 |

**この音源ではDSPのピーク追跡が最良**という結果になった。理由は明確で、合成音源は

- 倍音が整数倍にきれいに並び、基音が最も強い（倍音除去が確実に効く）
- 部屋の残響・マイク特性・演奏ノイズがない
- 打鍵ごとに明確なスペクトル変化がある

ため、ピーク追跡にとって理想条件だから。**実ピアノ＋スマホマイクでは、非整数倍音・うなり・残響・ノイズでピーク追跡が崩れやすく、学習モデルが有利になる**と予想される。この比較は「DSPは捨てる」ではなく、**ライブの鍵盤点灯や一次検出にはDSPを併用する価値がある**ことを示している（§8）。

NMFは辞書の音高分離が不十分で（近接音程のテンプレートが同一ビンに重なる）、実用に届かなかった。採用しない。コードは比較記録として残す。

計算コスト（参考・Python実装）:

| 検出器 | 9秒音源の処理時間 | 備考 |
|---|---|---|
| Basic Pitch | 130 ms（2秒窓×6回） | 窓あたり23 ms |
| スペクトルピーク | 77〜350 ms | 純Python。Kotlin/NDKなら大幅に高速化可能 |

## 7. 実測4: チャンク処理（LiveTranscriber）

### 7.1 処理方式

`phase0-poc/pianosheet_poc/live.py` の `StreamingTranscriber` が仕様書 4.3 の流れをそのまま実装している。

```
push_audio_chunk（AudioRecordの100ms読みに相当）
  → リングバッファ（窓長以上を保持）
  → step ごとに「直近 window 秒」を切り出し
  → モデル推論＋復号
  → 候補の整理（下記4段）
  → 新規イベントのみ UI へ
```

候補の整理は4段階:

1. **減衰尾の除去**: `onset_strength < 0.30` を捨てる（§5）
2. **確定済み区間の除外**: すでに表示した時刻より前の候補は捨てる。窓は重なるので、モデルは毎ステップ過去の音符も返してくる（実測で**候補の73〜90%がこれ**）
3. **保留（guard）**: 窓の末尾 `guard_ms`（既定260 ms）に入る発音は、直後の音声がまだ無く判定できないため**次のステップに回す**。捨てない
4. **統合**: 残った候補のうち、同じ音高で発音時刻が120 ms以内、または「弱い onset で直前の同音の余韻に連続している」ものは同一音符として統合

### 7.2 精度・遅延・負荷（全14テスト合計）

| window | step | conf下限 | マイクロF1 | P | R | 候補 → 確定済み除外 → 統合 → 新規 | 遅延 中央値 | 描画遅延 p95(最大) | ステップ推論 p95 | 実時間比 |
|---|---|---|---|---|---|---|---|---|---|---|
| **2.0s** | **0.25s** | 0 | **0.901** | 0.876 | 0.928 | 2585 → 2142 → 134 → **234** | **377 ms** | **552 ms** | 32.5 ms | **0.103** |
| 2.0s | 0.5s | 0 | 0.884 | 0.859 | 0.910 | 1351 → 981 → 101 → 234 | 520 ms | 782 ms | 25.2 ms | 0.056 |
| 2.0s | 0.25s | 0.45 | **0.911** | 0.921 | 0.901 | 2585 → 1925 → 129 → 216 | 377 ms | 549 ms | 28.6 ms | 0.105 |
| 1.5s | 0.25s | 0 | 0.901 | 0.876 | 0.928 | 2195 → 1768 → 134 → 234 | 377 ms | 550 ms | 24.7 ms | 0.100 |
| 1.0s | 0.25s | 0 | 0.899 | 0.872 | 0.928 | 1768 → 1357 → 130 → 235 | 375 ms | 550 ms | 26.1 ms | 0.102 |
| 2.0s | 0.1s | 0 | 0.896 | 0.862 | 0.932 | 6383 → 5740 → 240 → 239 | **311 ms** | 422 ms | 27.9 ms | 0.243 |

- **遅延の定義**: 「発音時刻」から「その音符を表示できたステップの音声時刻＋推論時間」まで。全テスト・全設定で **2秒以内に収まる割合 100%**（`frac_within_2s = 1.0`）。
- **窓を2.0秒から1.0秒に短くしても精度はほぼ落ちない**（0.901 → 0.899）。モデルは内部で2秒を見るが、実音声が短くても左をゼロ埋めすれば動く。Phase 1 では**メモリと遅延の余裕を見て1.0〜2.0秒で調整可能**。
- step を 0.25 → 0.1 秒にすると遅延は 66 ms 改善するが、CPUは2.4倍（実時間比 0.24）。バッテリーとのトレードオフになる。
- 実時間比 0.10 は「音声1秒あたり推論の壁時計時間が0.1秒」（2スレッド時。CPU時間では約0.2秒）を意味する。**10倍の余裕**がある。

### 7.3 保留時間（guard）のスイープ

guard は「窓の末尾どれだけを判定保留にするか」で、遅延の下限を直接決める。

| guard | マイクロF1 | P | R | 遅延 中央値 | 描画遅延 p95 |
|---|---|---|---|---|---|
| 120 ms | 0.886 | 0.883 | 0.890 | 293 ms | 398 ms |
| 180 ms | 0.883 | 0.877 | 0.890 | 311 ms | 468 ms |
| **260 ms** | **0.908** | 0.911 | 0.904 | 386 ms | 528 ms |
| 360 ms | 0.900 | 0.904 | 0.897 | 526 ms | 631 ms |

260 ms が最もバランスが良い（Basic Pitch の最小音符長 128 ms ＋ エネルギー判定に必要な余裕として妥当）。**遅延予算1〜2秒に対して十分な余裕がある**ため、Phase 1 では 260 ms を初期値にする。

### 7.4 チャンク境界の重複・欠落

- **重複**: 素朴に「2秒窓を0.25秒ごとに復号してそのまま並べる」と、同じ音符が何度も返り、イベント数は 480〜545個（正解は約230個）に膨らんで **F1 0.39〜0.52** まで落ちた。§7.1 の整理を入れると、**統合が必要だったのは134件（候補の5.2%）**まで減り、F1 0.901 になった。つまり重複のほとんどは「確定済み区間の再検出」であり、これを最初に落とすのが最も効く。
- **欠落**: guard を入れたことで「窓の末尾に来た音符を捨ててしまう」問題は解消。T-003（280ms連打）でも取りこぼしゼロ。guard を入れないと、窓の端の音符は判定できないまま確定済み扱いになり、そのまま失われる。
- **境界での音符分割**: 窓の端で切れた音符は、次のステップで完全な形で再検出され、発音時刻が同じなので統合される（T-002 の3秒保持でイベント1個を確認）。

| 26.85秒セッション | wall 2.73 s / CPU 4.38 s / 実時間比 0.10 / 決定論的（2回実行で完全一致） |

### Android での見積り

- **モデルの小ささが決定的**。230 KB（ONNX）／200 KB（TFLite版も同梱されている）で、アプリに同梱しても問題ない。パラメータ数が少ないため、スマホのCPUでも1回の推論は**数十ms台**に収まる見込み。
- 0.25秒ステップなら、1回の推論に**250 msの予算**がある。仮にAndroidの中位機が本検証機の3〜5倍遅くても（70〜175 ms）、**まだ余裕がある**。1スレッド35 msの5倍＝175 msでも実時間比 0.7。
- したがって「端末内推論で1〜2秒目標」は**十分に達成可能**。サーバー推論に頼る必要はない（仕様書 9.3 の第一候補を維持）。
- 実機では **ONNX Runtime Mobile** と **TFLite（LiteRT）** の両方を同じ `LiveTranscriber` インターフェースの裏で測り、発熱・バッテリー・初回ロード時間で選ぶ。量子化（int8）はモデルが既に小さいため優先度は低いが、速度が出ない場合の選択肢として残す。
- 注意点: 実機ではサーマルスロットリングと省電力モードで推論が遅くなる。**遅延が目標を超えたら step を 0.25 → 0.5 秒に落とす**フォールバックを Phase 1 で実装する（実測でも step 0.5 で F1 0.884、遅延 520 ms と実用範囲）。

## 9. 採用する構成（Phase 1 への推奨）

### 9.1 LiveTranscriber（録音中）

```
AudioRecord 44.1/48kHz 16bit mono（専用スレッド）
  → 100 ms チャンクでリングバッファへ
  → 22.05kHz へリサンプル（ポリフェーズ）
  → 250 ms ごとに「直近 2.0 秒」をモデルへ
  → Basic Pitch ONNX（または TFLite）
  → 復号（閾値 onset 0.5 / frame 0.3 / 最小音符長 128 ms / melodia）
  → 候補整理（onset_strength ≥ 0.3 → 確定済み区間の除外 → guard 260 ms → 統合）
  → NoteEvent（state=provisional）を StateFlow へ
```

- 期待性能: **遅延 中央値 0.38 秒 / p95 0.55 秒**、和音・連打を含む F1 **0.90**
- 鍵盤点灯は `onset_strength` と `pitch_midi` から即時に行う（モデル出力だけで足りる）
- **補助としてスペクトルピーク検出器（11.6 msフレーム）を併走**させる価値がある。実装は軽く（FFT 1回/フレーム）、モデルが落とした打鍵の検出補助と、入力レベル／ノイズ状態の表示に使える。モデル出力との衝突は `onset_strength` の高い方を採用する

### 9.2 FinalTranscriber（録音停止後）

```
録音WAV全体
  → Basic Pitch 全体解析（0.35秒オーバーラップ窓）
  → onset_strength フィルタ ＋ 減衰尾の統合（連続する同音セグメントを1音符へ）
  → 長さ推定（減衰・ペダルを考慮）→ テンポ・拍子・調性 → 量子化 → 小節化
  → MusicXML / MIDI
```

- 実測 F1 0.85（onset_strength 適用後 0.88）。**音高・発音時刻はほぼ確定**しており、残る作業は長さ・リズムの整形
- ペダル（T-012）と速いパッセージ（T-010）は精度不足。Phase 2 で「長さ推定」と「同音連打の分割」に特化した後処理を入れる
- 端末内で完結可能（26.85秒の音声を2.7秒で処理）。**サーバーは必須にしない**

### 9.3 インターフェース（共通仕様）

`shared-specs/note-event.schema.json` に、仕様書 4.5 / 4.8 / 10.3 / 10.4 を統合した `NoteEvent` を定義した。`onset_strength` を追加した点が実測に基づく変更。Kotlin 側は `kotlinx.serialization` で同型を生成し、`LiveTranscriber` / `FinalTranscriber` は `Flow<List<NoteEvent>>` と `suspend fun transcribe(file): Score` に揃える。

### 9.4 Phase 1 の推奨パラメータ

| パラメータ | 推奨値 | 根拠 |
|---|---|---|
| サンプリングレート（内部） | 22,050 Hz | モデル要件。入力は44.1/48kから変換 |
| チャンク読み出し | 100 ms | AudioRecord の実装容易性、テストと同一 |
| 解析窓 | 2.0 s（メモリ制約があれば1.0 s） | 1.0秒でも精度 0.899 |
| ステップ | 250 ms | 遅延377ms、CPU 0.10。負荷が高ければ500 msへ |
| guard（保留） | 260 ms | §7.3 |
| onset閾値 / frame閾値 | 0.5 / 0.3 | 上流既定。変更しない |
| 最小音符長 | 128 ms（11フレーム） | 上流既定 |
| onset_strength 下限 | 0.30 | §5 |
| 統合の時間幅 | 120 ms（同音） | §7.4 |

## 11. Phase 1 へ進む準備

**進められる。** 根拠:

1. 端末内推論で遅延・負荷ともに目標の1〜2秒に対して**3〜5倍の余裕**がある（§8）
2. 和音・連打・保持を含む**ライブ処理のF1 0.90**を、チャンク境界の重複・欠落なしで達成
3. 共通 `NoteEvent` と `LiveTranscriber` / `FinalTranscriber` の分離が、実装済みのPythonコードで検証済み（同じ構造をKotlinへ移植可能）
4. モデルは 230 KB で、**TFLite版も同梱**されており Android への組み込み障壁が低い

Phase 1 の着手順（仕様書 19章の順序に一致）:

1. Kotlin/Jetpack Compose プロジェクト作成、AudioRecord で 22.05kHz への変換まで
2. ONNX Runtime Mobile / TFLite で 2秒窓の推論を実機で測る（このレポートの数値と比較）
3. §9 のパラメータで `LiveTranscriber` を実装、`NoteEventRepository` に3段の整理を入れる
4. 大譜表への暫定表示・音符カウンター・鍵盤点灯
5. 実機マイク録音（T-013）で精度を再測し、しきい値を調整
